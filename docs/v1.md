# La v1 (wishme.fr) — état au 2026-10-09

Ce qui tourne aujourd'hui en production, ce qu'il faut migrer, et ce qu'il ne faut pas reproduire.

## Stack
- **Client** : React 18, Vite, Tailwind, Headless UI, TanStack Query, react-hook-form + yup, i18next (fr, en), mode sombre.
- **Serveur** : ASP.NET Core 8, Identity (cookies), EF Core + PostgreSQL 16, Google Sign-In (token validé côté serveur), e-mails SMTP.
- **Infra** : 3 conteneurs Docker (Postgres, API, client Nginx) sur un serveur, certificats Let's Encrypt montés à la main.
- **CI** : un workflow qui build et pousse les images Docker sur `main` (`latest`) et `beta` (`beta`). Aucun test, aucun lint en CI, aucun déploiement automatique.

## Modèle de données
| Table | Champs utiles | Remarques |
|---|---|---|
| `AspNetUsers` (Identity) | `Id` (Guid), `Email`, `PasswordHash`, `DisplayName` (≤30), `RecentWishlistIds` (Guid[]) | Hash mot de passe au format Identity v3 (PBKDF2), non importable tel quel ailleurs |
| `AspNetUserLogins` | `LoginProvider` = `Google`, `ProviderKey` (sub Google) | Lien compte Google ↔ utilisateur |
| `Wishlists` | `Id`, `UserId`, `Name` (≤30), `CreatedAt` | |
| `Items` | `Id`, `WishlistId`, `Name` (≤255), `Url` (≤2048), `Price` (float), `BuyerIds` (Guid[]), `CreatedAt` | Pas de devise, prix en `float` |

## Fonctionnalités
- Inscription e-mail + mot de passe + nom d'affichage ; connexion e-mail/mot de passe ou Google ; mot de passe oublié par lien e-mail ; changement de mot de passe ; modification du nom d'affichage.
- Créer, consulter, supprimer une wishlist (renommer : impossible).
- Ajouter, modifier, supprimer un souhait (nom, prix, lien).
- Partager : copie de l'URL de la wishlist. Le lien est le seul contrôle d'accès.
- Un visiteur connecté « réserve » un souhait (`pick`) ou annule ; les autres visiteurs voient qui a réservé ; le propriétaire ne le voit pas dans l'interface.
- Page « récentes » : wishlists des autres consultées en étant connecté.
- Lecture anonyme : retirée de l'interface en déc. 2024 (redirection vers la connexion), mais l'API la sert toujours.

## Failles à ne pas reproduire
1. **N'importe quel utilisateur connecté peut ajouter un souhait dans la wishlist de quelqu'un d'autre** : `ItemsService.CreateItemAsync` ne vérifie pas le propriétaire.
2. **La surprise est éventée par l'API** : `GET /api/wishlists/{id}` renvoie `buyerIds` à tout le monde, propriétaire et anonymes compris. Seule l'interface les cache.
3. Un même utilisateur peut réserver plusieurs fois le même souhait (`BuyerIds` est une liste sans contrôle d'unicité).
4. Le nom d'affichage de n'importe quel utilisateur est lisible sans authentification à partir de son Id.
5. Mot de passe de la base en clair dans `docker-compose.yml`.
6. Aucune politique de confidentialité, aucun moyen de supprimer son compte ou d'exporter ses données (obligations RGPD).

## Contraintes de migration
- Conserver les Guid existants (utilisateurs, wishlists, souhaits) : les liens déjà partagés doivent continuer à fonctionner.
- Les hash de mot de passe Identity ne seront probablement pas réutilisables : prévoir que ces utilisateurs se reconnectent par code e-mail (OTP), qui devient la méthode par défaut, puis redéfinissent un mot de passe s'ils le souhaitent.
- Les comptes Google se rattachent par l'e-mail et le `sub` Google.
- `RecentWishlistIds` et `BuyerIds` deviennent des tables de liaison.
- Prix : passer de `float` à un montant entier en centimes + devise (EUR par défaut).
